# 子 Agent 派活规范（v1）

> **适用场景**：主控（本体）不亲自逐块重排，而是**把单章/单组派给子 agent 转写**，主控当组长负责派活、验收、推进。适合**章节多、体量大**的成批转写。
> **它与 `orchestration-manual.md` 的关系**：编排手册讲的是「本体**亲自**逐块重排」的 10 步流程；本规范讲的是「**派出去**」的变体——适用章节多、体量大的批量转写。
> **依据**：在两本入门教材上实跑 11 个章节单元（含一轮全书独立复审）的实证。
> **配套**：`prompt-family-p1-p5.md`（转写规则）、`capability-functions.md`（脚本能力）、`gate_check.py`（门禁）。

---

## 一、前提与默认节奏

本文档描述一种**把单章/单组派给子 agent、主控只当组长**的批量转写做法。默认节奏如下——**标【硬要求】的不可省，其余可按你的项目规模与偏好调整**：

1. **一次只跑一个子 agent、串行推进**（默认节奏）。好处是主控能逐章核验、问题不累积；章节多、想提速也可以并发，但**验收环节不能省**。
2. **每章/每组做完停下确认**（默认节奏），不连跑。
3. **主控当组长**：派活 + 独立验收 + 更新进度。**【硬要求】**
4. **验收必须自己做，不采信子 agent 自报**（见第七节）。**【硬要求】**
5. **笔记定位 = 给 AI 看的教学素材库**，不是给人从头读到尾的教科书 → **厚度保持**，不因膨胀率高而精简。

---

## 二、派活前：组长必做的"摸源"

**不许拿到源文件就直接派活。** 先自己读一遍源，把这一章/组特有的坑摸出来，写进提示词。

已证实的收益：正是这一步让缩进整体丢失、元素与注释错位、乱码函数名等破坏在派活时就被点名，子 agent 才不会照抄坏代码。

摸源时至少确认：

- 这一章/组的**骨架**（章？习题？各多少）
- **源文破坏形态**（对照第四节清单逐项看）
- **版本差异点**（源文档是不是老版本？有没有会变的输出？）
- **哪些地方必须实跑验证**（算例、输出、断言）

---

## 三、派活提示词必备要素（十项）

1. **角色与任务**
2. **输入清单**：源文件路径 + 格式样板 + **同书前作**（保持一致）+ 转写规则全文
3. **笔记结构**：frontmatter / 概述 / 六件套知识点 / 术语表 / 自测题 / 元信息
4. **⚠️ 本章特有的坑**——逐个写明「源文现状 → 应还原为什么」。**这是提示词里最有价值的部分**
5. **硬性质量规则**：六件套齐全 / 费曼每点≥2 / 膨胀率≥80% / 机械对账≥90%
6. **⭐ 自加内容纪律**（见第五节，本规范最重要的一条）
7. **禁止元评论进正文**（"源文印错了"只能进元信息）
8. **输出路径**（写死，不许改名换地方）
9. **门禁命令**（写死，含 `PYTHONIOENCODING=utf-8`）
10. **交付报告格式**，并明确要求"**如实报告存疑点，不许美化**"

## 四、源文破坏形态清单

派活前对照这张表逐项检查；命中就写进提示词第 4 项。

| 形态 | 典型表现 | 处理 |
|---|---|---|
| **缩进整体丢失** | `if:` 下的语句与关键字齐平 | 按语法补回（4 空格一层） |
| **代码被拆成多块** | 一个程序被切成 2~3 个代码块 | 合并成完整块 |
| **行号污染** | `15 target.truncate()`、`19 print_two(...)` | 去掉行号 |
| **输出块插进代码中间** | 终端输出夹在前后两段代码之间 | 把输出块与代码块分离 |
| **三引号被拆坏** | `print ""` 后跟正文、`"""` 孤零零在末尾 | 还原成 `print """` … `"""` |
| **LaTeX 假公式** | `$+ =$`、`$a + b$`、`\text {words = 'words' * 3}` | 还原成代码 |
| **HTML 表格** | `<table><tr><td>` | 还原成 Markdown 表 |
| **元素与注释错位** | 注释整体错一位、元素被吃掉 | 按类型对应还原 + 登记 |
| **反转义残留** | `raw\_input`、`\$env:Path`、`con\*cat\*enate`、`100\*6` | 还原原字符 |
| **命令行被误标成标题** | `## pip --version`、`## cd C:\download` | 还原成代码块 |
| **乱码** | `ppmake_name`、`Energythere`、`print缺口{...` | 按上下文修正；**不确定就不补，显式标注** |
| **语言标记错误** | `lua` / `perl` / `javascript` 标在非该类代码上 | 改 `python` / `bash` / `txt` |
| **括号错位** | `紧跟着括号（？`、`函数是否以）结尾？` | 还原半角括号 |
| **边栏被当标题** | `## Note` / `## Warning` / `## 加分习题` | 按语义并入知识点正文 |
| **画面描述块混入** | 图文书里的 logo 图标、装饰插画 | 判价值：含知识的吸收，纯装饰丢弃 |

### ⚠️ 反向陷阱：**看起来像错、其实是设计——不许改**

上表讲的是"要修的破坏"。但还有一种情况恰好相反：**源文里有个明显的"错"，却是作者故意写的教学装置**。

**实例**：某习题的交互式会话里故意写了 `wrods`（`words` 的拼写错），用来演示 `NameError`；正文里作者明说了「我把 words 变量写错成了 wrods」。

**如果转写者把它"纠正"成 `words`，这个教学点就整个毁了**——那一段的全部意义就是"让你看见拼错变量名会怎样"。

**判别依据（重要）**：

| 情况 | 判据 | 处理 |
|---|---|---|
| **OCR 破坏** | 源文自相矛盾、语法不成立、与上下文不搭 | **修**（见上表） |
| **作者的设计** | **正文/注释里有明文说明**，或改动后有明文说明 | **原样保留** |
| **两者都不是** | 拿不出依据 | **不许猜**（见第五节补充情形） |

**一句话：能拿出来源的修正才是修正，拿不出来的就别动。**

## 五、⭐ 自加内容纪律（最高优先级）

**这是用 4 个 P0 错误换来的教训，不许省。**

### 铁律

> **源文给的样例输出、代码运行结果、以及任何"某段代码会怎样"的断言，必须先自己实跑或复算一遍再写。**
> **实测与源文不一致时，照实写实测结果并显式标注"源文此处与此不符"。**
> **绝对不许照抄源文结果、再补一段解释去圆它。**

### 为什么（实证）

一轮全书复审抓出的 **4 个 P0 全部出自"自加内容"**，形态高度一致：

> **源文自身有错 → 转写时照抄 → 转写者又自加一段解释，把错误"圆"成合理的。**

三个实例：
- 字符串拼接一节：书上输出多带空格，笔记照抄**并编了"因为变量自带空格正好凑成一句"**
- 函数参数一节：书上说某行代码"能正常运行"（实为 SyntaxError），笔记照抄**还加了 `# RIGHT!` 注释和"为什么能跑"的思考题**
- 数据结构一节：书上把 `print(1)` 列为"函数"，笔记照抄**还补了"列表不会自动执行它"**

**共同点：不是被动复制错误，而是主动为错误辩护。** 这类错误读起来自洽、有解释、有推理，肉眼扫过去不像错的。

**根因**：转写者的本能是"让内容讲得通"，遇到前后对不上会下意识补解释弥合，而不是回头质疑源文。

### 补充情形：查不清原文时，**不许猜**

有一类比上一条更微妙：**源文与实测不符，但你无法判断原书到底怎么写的**（典型：源文代码印得残缺，实测结果与源文印的输出对不上，两种解释都说得通）。

**处理方式：两种可能都留在元信息里，正文按实测写并标注差异，绝不擅自"修"成其中一种。**

实例：某习题代码写的是 `know'bout`（无空格），而书里印的输出是 `know 'bout`（有空格）。合理推测是原书代码为 `know 'bout`（OCR 吃掉了空格），**但这是推测、没有依据**——正确做法是**把推测与事实分开摆出来**，而不是替原作者"改对"。

**判据**：改动的依据必须来自 (a) 源文明文，或 (b) 可执行的实跑结果。**两者都没有时，标注存疑，不动手。**

#### 变体：**源文自己跟自己矛盾**

上一条讲的是"源文与实测不符"。还有一种：**源文的两个部分互相矛盾**（最典型是**代码块与输出块对不上**）。

**这时同样不许判定谁对谁错**——因为"谁是对的"这个依据，源文里根本没有。

**做法：两者都按原样保留，把矛盾显式摆出来，让读者自己跑一遍判断。**

**实例**：某习题的代码写的是 `''.join(列表)`（空字符串连接），同一页印出的输出却**带着空格**。实测：`''.join` 得**无空格**、`' '.join` 才得带空格——**代码与输出只能有一个是对的，而源文没给判断依据**。正确处理是**代码照抄、输出照实写、加一段说明把矛盾摊开**；**不是**替作者把代码改成 `' '.join`。

**为什么留着矛盾更好**：这类书（尤其是"照着敲、自己跑"式的练习书）本来就在训练读者"**把自己跑出来的结果和书上印的对比，找出不同点**"。**把矛盾留着，恰好是给读者的练习**；替他们"修好"，反而把这个练习抹掉了。

**判断口诀**：**能指出来源的修正才叫修正**（源文明文 / 实跑结果）；**指不出就直接改，那是猜。**

### 效果（实证）

加上这条之后，后续各组**每次都能自己揪出源文与实际不符**（报错措辞、输出句点数、点号个数、空格数等），且都是**照实改写 + 标注差异**，不再是编解释圆场。

## 六、版本差异处理法（老书专用）

**原则：原样保留 + 并列新写法 + 逐处提醒 + 概述里的总时代标注。**

**绝不**简单替换成新版就完事（那就不是这本书了）；**也绝不**只留旧写法（AI 拿它教学会教出作废语法）。

### 常见类型

| 类型 | 例子 | 处理 |
|---|---|---|
| **改名** | `raw_input()` → `input()` | 并列，标"今天会报 NameError" |
| **语句变函数** | `print "x"` → `print("x")` | 并列 |
| **行为改变** | 整数除法 `1/4`：`0` → `0.25` | **实测数字 + 书里原值两列对照** |
| **报错措辞变** | `need more than 3 values to unpack` → `not enough values to unpack (expected 4, got 3)` | 正反两向都写 |
| **⭐ 版本撞车** | 变量名 `input` 在旧版无害、在新版遮蔽内建函数导致 `TypeError` | **单独成节**——这不是"换了名字"，是"两个东西撞到一起" |
| **API 移除** | `time.clock()`（3.8 移除）、`file` 类型（新版无） | 标注 + 给替代 |
| **平台/工具过时** | 编辑器、安装方式、软件菜单路径 | 标注 + 说今天怎么做 |
| **建议已反转** | "忽略提到新版本的项目"（十多年前对，今天完全反了） | **原文照录 + 显式说明已反转** |

### 量化提醒

- **不是所有差异都会露出来**：`%d` 会把浮点截成整数，掩盖整数除法差异；`%s` 或用逗号连接就会露。**同一个坑，有的地方掩盖、有的地方露馅——这个对比本身有教学价值**，值得讲。
- 老文档的输出**不能直接当实测结果用**：本机通常没有旧版运行环境，**"书里印的"这一列必须明确标注是原文、不是实测**。

### ⚠️ 验证原则：**验对象，不要只验"能跑"**

实测时最容易犯的错是"跑通了就认为等价"。**跑得动 ≠ 结果对**。

**实例**：老书里有道题问"能不能把 `range(0,6)` 直接赋给变量、不用循环"。新版语言里这一步**照样能跑**——后面接同一个 `for` 循环，输出**一模一样**。只看"能不能跑"，会得出"老书答案仍然成立"的错误结论。

**真正的差别在对象本身**：类型变了、`repr` 变了、和列表比较是 `False`、调用某些方法直接报错、内存占用从"随规模增长"变成"恒定"。

**所以验证要往这几个方向戳**：

| 戳哪里 | 怎么戳 |
|---|---|
| 类型 | `type(x)` |
| 显示形式 | `repr(x)` —— 打印出来长什么样，不等于它是什么 |
| 等价性 | 用 `==` 和不转写的结果比，别靠肉眼看输出 |
| 可用性 | 调一个"应该能用的方法"，看会不会报错 |
| 规模行为 | 换个尺度的输入，看内存/耗时是否随规模变化（能暴露惰性求值） |

**一句话：输出相同不代表东西相同。**

### 反向适用：**派活单自己的技术断言，也要被核对**

上面几条都是要求子 agent 核对**源文**。但同样重要的一条是：**组长写在派活单里的技术断言，也可能不准**——子 agent 应当实测核对，**对不上就顶回来并说明**。

**实例**：组长在派活单里写"这个库今天根本装不上"。子 agent 实测发现：**能装上**（包还在源上），真正的问题是**导入时崩**（内部依赖的一个模块在新版本被移除了）。它按实测写，并明确标注"与本任务书表述有差异"。

**为什么这条重要**：派活单是**人写的**，会带进人的记忆误差；而**子 agent 手上有实测能力**。如果它盲从派活单，那个错误就会一层层传下去、最后写进交付物。

**给组长的要求**：派活单里的每个技术断言，**要么标明"我实测过"，要么标明"待核实"**。前者子 agent 可以采信但要复核，后者必须实测。

**给子 agent 的要求**：派活单里的技术断言**不是圣旨**——**与实测冲突时按实测写，并在报告里显式说明分歧**。

## 七、组长验收清单（每章/组必做）

**不采信子 agent 自报。** 逐项自己跑：

1. **重跑门禁**（同一命令）——看判定行是否 PASS
2. **代码语法自查**：抽出所有 `python` 代码块，逐个 `ast.parse`（**先 `textwrap.dedent`**，Markdown 列表里的代码块带缩进）
   - 注意：**故意演示报错的代码块"非法"是预期的**，要能分辨
3. **核对它声称的每一处修复**——它说改了 X，就去文件里搜 X，确认真改了
4. **抽读内容**：至少读最关键的 1~2 个知识点全文，看类比是否成立、算例是否可疑
5. **独立复现它报的"实跑发现"**——它说"实测是 Y"，自己跑一遍确认
6. **更新进度表**
7. 发现问题 → **就地修正**（小瑕疵）或 **报告出来等确认**（大改动）

## 八、命令速查

```bash
# 门禁（PYTHONIOENCODING 不能省，否则 emoji 在 Windows 控制台崩溃）
cd <_md_rewrite_tools>
PYTHONIOENCODING=utf-8 python scripts/gate_check.py "<笔记.md>" --src "<源.md>"

# 图文书源过滤（保留 GLM 画面理解）
PYTHONIOENCODING=utf-8 python -m scripts.filters.ebook_source_filter \
  --src "<full_embedded.md>" --out "<clean_only.md>" --keep-glm

# 文字型 PDF 源过滤
PYTHONIOENCODING=utf-8 python -m scripts.filters.ocr_source_filter \
  --chapter <N> --src "<章节_clean.md>" --out "<章节_clean_only.md>"
```

**代码块语法自查**（内联脚本）：

```python
import re, ast, pathlib, textwrap
t = pathlib.Path("<笔记.md>").read_text(encoding="utf-8")
for i, b in enumerate(re.findall(r"```python\n(.*?)\n[ \t]*```", t, re.S), 1):
    try:
        ast.parse(textwrap.dedent(b))
    except SyntaxError as e:
        print(f"#{i}: {e.msg}")
```

## 九、门禁指标的正确解读

- **膨胀率不构成质量信号**：笔记体量由「知识点数 × 六件套」决定，**有下限且相对恒定**，与源大小无关。所以源越小、膨胀率越高（实测 96% ~ 540%），这是分母问题不是内容问题。**门禁只卡下限 ≥80% 防偷工。**
- **真质量判据**：机械对账（≥90%）+ 六件套 + **内容抽读** + **独立复审**。
- **术语变体（warning 级）信噪比低**：实测几乎全是滑窗碎片误报（如「学习方法」→「学习方面」这种窗口边界刚好差一字的相邻短语），**逐条人工看一眼即可，不进判定**。

## 十、批次收尾：独立复审

**每本书/每批转完后做一次，派 2 个审查 agent 分头审**（各管一半）。

审查 agent 的提示词必须包含：

1. **先读每篇的「📌 元信息」**——那里面登记了所有"故意修复"，不先读会把正确行为当成错误来报
2. **重点盯「自加内容」**——最高风险区（见第五节）
3. **能实测的实测**（给它 Bash + Python）
4. **只报告，不修改任何文件**
5. **不许为了交差编造问题**——没找到就写"未发现 P0/P1"。**凑数报假问题比漏报更糟**
6. 分级：P0 事实错误 / P1 不一致 / P2 遗漏 / P3 小瑕疵
7. 每条必须给证据（位置、原话、为什么错、正确是什么）

**复审后的修正**：改动逐条核对、改完重跑门禁确认无退化、**给各章元信息补"审查后修正"登记**。
