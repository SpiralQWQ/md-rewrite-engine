# 重引擎评估报告（C3c）· 2026-08-14

> **问题**：是否引入 llm-wiki-compiler（npm）作为完整重排引擎，替代自研 `md-rewrite-engine` 的滚动编译。
> **结论**：**维持自研，不引入。**

## 一、llm-wiki-compiler 是什么
Karpathy LLM Wiki 生态的重型实现（npm/Node.js），覆盖 AI 重排 + 质量门禁 + 溯源。

## 二、引入利弊对比

| 维度 | 引入 llm-wiki-compiler | 维持自研 |
|---|---|---|
| 技术栈 | **Node.js/npm 生态**，与 Python 栈冲突 | Python 轻量，与现有栈一致 |
| 核心能力 | AI 重排 + 门禁 + 溯源 | 自研已覆盖：rolling_compile + verify（对账/评分/语义对账）+ D 系列（互链/索引/概念页/置信度） |
| 教学结构 | 通用 wiki，**无 7 栏目+费曼** | ✅ 独有教学结构（769 仓无人有） |
| 中文支持 | 英文优先 | ✅ 中文为主 |
| 集成成本 | 跨语言调用（Node 子进程/服务）+ 依赖注入 | 零额外依赖 |
| 维护 | 依赖上游活跃度 | 全自控 |

## 三、结论
1. **自研已覆盖其核心价值**：滚动编译（重排+摘要贯穿）+ 确定性验证层（双模型质检/语义对账/评分门槛）+ 溯源，均为自研实现。
2. **教学结构是差异化**：llm-wiki-compiler 是通用 wiki，我们的 7 栏目 + 费曼 + OKF 是独有优势，引入反而丢失。
3. **技术栈冲突**：Node/npm 与 Python 栈集成成本高，违反轻架构原则。
4. **不引入**；如需借鉴，其"质量门禁由写路径强制"思想已通过 verify 层落地。

## 四、影响
- 零生产代码改动；评估结论留档，避免未来重复调研。
